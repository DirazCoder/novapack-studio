NOVABYTE STORE
Get your app reviewed and listed

On the NovaByte Store website, sign in, choose Publish apps, and complete the submission form with your unsigned .novaapp; self-signing isn’t needed. Submissions go through automated checks and human review. If approved, NovaByte preserves your existing tamper-protection method or adds protection if it’s missing, then signs the app with Ed25519. Any other signature is replaced before the app is listed.

The rules are on the Store website: open Publish apps and expand Store requirements in the form.

Development keys are not publisher trust

Self-signing proves a package matches your key. It does not make NovaByte OS trust the publisher.

Your first project, start to finish

            
NovaByte Studio is a desktop IDE for building and packaging .novaapp apps for NovaByte OS and compatible NBOSP systems. Use the left sidebar to create or open a project; once it is open, the project tabs contain the editor, manifest, permissions, design, build, and review tools.

            
    
              
  1. Create or open a project. Choose New Project and a starter that is close to your app, or use Open Folder for an existing project. Templates provide example files you can change or remove.
    2. 
              
  2. Explore the project tree. Open the HTML entry page and its related CSS/JavaScript files. Create, rename, and organize files from the tree; save edits with Ctrl+S / Cmd+S or turn on autosave in Settings.
    3. 
              
  3. Set the app identity. In Manifest, choose a readable name, a unique lowercase reverse-domain ID such as io.example.notes, a version, and the correct entry HTML path. Save the manifest before building.
    4. 
              
  4. Declare only needed permissions. In Permissions, add each capability the app actually uses and write a clear reason. Optional permissions are for sensitive features requested only when the user chooses to use them.
    5. 
              
  5. Preview and validate. Use the HTML preview or Design tools to catch layout issues, then inspect the Build contents preview and resolve any manifest or permission validation messages.
    6. 
              
  6. Build and verify. Open Build, choose the output location and options, then build. Use Package Inspector on the resulting .novaapp to review the packaged manifest, included files, integrity, and signature information.
    7. 
            

            
Pick a starting point

            
Use a focused template such as blank, webapp, browser, utility, game, dashboard, form, markdown-viewer, or chat. If none fits, start blank and add only the files and permissions your app needs. Open an existing project by selecting its project folder, not the generated dist folder.

            
Studio remembers your theme, compact/comfortable density, blur and glass preference, autosave choice, pane widths, dock sides, and collapsed panes on this device. Change them in Settings or by resizing the pane handles; they are applied as the window opens.

            
 Keep working files in the project folder. Before sharing a project or exporting a starter, check it for credentials and private data; build filters are not a substitute for reviewing what you ship.

          


          

            
Editing and visual design

            
Work with project files

            
    
              
  1. Select a file in the project tree to open it in the editor. Use Ctrl+P when you know the filename, or the Command Palette with Ctrl+Shift+P to find an action.
    2. 
              
  2. Use editor tabs to move between files. The dirty marker means a file has unsaved changes; save with Ctrl+S / Cmd+S, or enable real-time or interval autosave in Settings.
    3. 
              
  3. For HTML, open the preview pane to check the page while you work. Relative images, stylesheets, and scripts should be stored in the project and referenced with paths relative to the HTML file.
    4. 
              
  4. Use project search to find text across files and Find / Replace for the current file. Review results before applying a replace-all operation.
    5. 
            

            
Use the Design tab

            
    
              
  1. Open the app's HTML entry file first, then select Design. The preview represents that page; if it is blank, confirm the manifest entry path and that the file exists.
    2. 
              
  2. Select an element in the preview to inspect it. Use the element tree and inspector to adjust supported content, attributes, and styles, then check the preview again.
    3. 
              
  3. Return to the editor to review the generated source changes. Keep complex behavior in your own CSS and JavaScript files, then use preview to verify the result.
    4. 
            

            
Studio's preview is a development aid, not the NovaByte OS runtime. Test OS APIs, permission prompts, and final window behavior on the target system too.

          


          

            
Manifest format

            
Every app needs a manifest.json at its root. Required fields:

            

              
FieldDescription

              
idUnique app ID, reverse-domain format (e.g. com.example.app)

              
nameDisplay name shown in the OS

              
versionSemantic version x.y.z

              
entryMain HTML file to load

            

            
Edit these fields in the Manifest form, then use View JSON to review the generated document and Save manifest.json to write it into the project. Set the entry to a real HTML file relative to the project root; if you move or rename that file, update the entry too.

            
Use the window controls to choose a sensible default size and, when needed, minimum/maximum sizes and whether the app can be resized. Test the app at its default size and near its minimum size so controls remain usable.

            
Optional fields include description, author, email, website, icon, type, permissions, optionalPermissions, permissionReasons, unrestrictedEntry, defaultSize, minSize/maxSize, resizable, frame, transparent, categories, handles, ipc, notifications, shareTarget, registryScopes, allowNestedWebview, allowPopupsToEscapeSandbox, and sandbox. Studio preserves manifest properties that are not edited in its form.

            
App IDs must be lowercase reverse-domain (io.github.you.app) — MyApp or myapp with no dot will fail validation at Build time. Web-app shortcuts use the webapp_ prefix instead.

          


          

            
Permissions

            
For each capability, ask: does this feature really need access, and can it wait until the user chooses the feature? Prefer an optional grant for sensitive, on-demand actions; remove permissions left over from a template.

            
Studio lists all 52 current permission strings. Declare required grants in permissions; missing medium-or-higher-risk grants may be requested at launch, but denial does not block the app. Optional sensitive grants in optionalPermissions are not prompted at launch and can be requested at runtime or granted from Settings → Apps. Low-risk grants are auto-granted unless previously denied. App-owned /data/ files and user-selected files do not need broad filesystem permissions.

            
Use Permission reasons in this tab to explain each grant. Studio saves the text in permissionReasons; NovaByte OS displays it in permission prompts. Reasons must be non-empty and at most 500 characters. A reason for an undeclared permission is preserved but unused.

Hover any permission in the Permissions tab (or in the manifest editor) for its exact risk level and description.

            
fs:access is special access enabled manually in Settings, never prompt-granted; shared media uses type-specific read grants, while picked documents are scoped to the user's selection. The legacy vfs:* names remain accepted by NovaByte OS for compatibility, but new apps should use fs:*. admin:* also requires machine Admin Access mode. system:root runs unrestrictedEntry outside the sandbox; it does not itself run Linux commands as root. mail:* acts on the account connected via the Email app.

          


          

            
Build a package you can verify

            
    
              
  1. Check the manifest. Resolve required-field, version, entry-file, and permission errors before building. The app ID is used in the output filename.
    2. 
              
  2. Review package contents. In Build, inspect the contents preview and any .studioignore exclusions. Make sure required files are included and local tests, logs, or secrets are not.
    3. 
              
  3. Choose output and build options. Set the output directory and whether to clean the last build. Named build profiles can save these choices, but do not store private signing keys.
    4. 
              
  4. Build, then read the result. Check the build status and history. The package is written as <app.id>.novaapp; use the Package Inspector to inspect it or compare it with another package.
    5. 
              
  5. Test on the target OS. A successful package build checks packaging, not every runtime behavior. Install and exercise the app on NovaByte OS / NBOSP, including permission-denial and empty-data cases.
    6. 
            

            
Signatures and integrity

            
Signing creates a signature associated with a key; an integrity hash detects package changes. They are separate settings. A self-signature or local-development signature does not establish publisher trust or make a package verified. Keep private keys out of project files, templates, and source control. Use the local development signing controls only for testing the last package built in Studio.

            
Builds that include detected C/C++ sources compile them to WebAssembly with emcc. Packaged Studio releases include Emscripten; source/development runs need Emscripten installed and available on PATH.

            
The Package Inspector reports signature validity separately from publisher trust. A valid signature means the package matches that signing key; it does not mean the key is trusted by the operating system.

          


          

            
Review changes with Source Control

            
    
              
  1. Open the Source Control view for the current project to review changed, added, deleted, and untracked files. File-tree badges are a quick signal, not a substitute for reviewing the diff.
    2. 
              
  2. Open each important change and inspect the diff before committing. Exclude generated output, local test data, credentials, and private keys from the repository.
    3. 
              
  3. Stage only the files that belong together, enter a message that explains the change, and create the commit. Keep unrelated work in separate commits when possible.
    4. 
              
  4. Use the branch controls to switch branches when needed. After switching, check the project tree and status again before continuing.
    5. 
            

            
Useful review tools

            
Use the diff / merge view to compare files, Build history to revisit a package build, and Package comparison to inspect changes between two .novaapp files. A clean Git status does not guarantee that the package contents are correct—review the Build contents preview separately.

            
If Source Control does not show a repository, open the actual project root and confirm it is a Git repository. Avoid committing signing keys, credentials, or files that should only exist on your machine.

Frequently asked questions


            
My app won't install / gets flagged on install — why?

            
An inline <script> block with real code in index.html is blocked by the install-time content scanner. Put the code in a sibling file and reference it instead:

            
<script src="app.js" defer></script>

            
For packaged apps, the host defers external entry-page scripts until HTML parsing is complete, so code in app.js can access elements declared in the page without a DOMContentLoaded wrapper. Keep defer to preserve the same behavior when testing outside NovaByte OS. Dynamically created scripts and documents keep normal browser timing.


            
Where do I put third-party libraries?

            
Drop single minified files (JS/CSS) into the vendor/ folder in your project — they're bundled automatically at Build time. Reference them as <script src="vendor/yourlib.min.js" defer></script>. Don't copy entire node_modules folders in.


            
My manifest permission isn't doing anything?

            
Studio lists all 52 current permissions in the Permissions tab. Some also require manifest opt-ins: sandbox:nested-webview needs "allowNestedWebview": true, sandbox:same-origin needs "sandbox": { "allowSameOrigin": true }, and sandbox:escape-popups needs "allowPopupsToEscapeSandbox": true. Both the permission and its opt-in are required. Low-risk permissions are auto-granted unless previously denied; denial does not block app launch.


            
Still stuck?

            
Open the Command Palette (Ctrl+Shift+P) and search for an action by name, or consult NOVAAPP.md in the Studio repository for the complete manifest, permission, and IPC API reference.
